Using the Package Catalog

Browse and download packages without an account. Downloads are DOS-XC .dsp files for the existing PKG installer.

Install and update

PKG INSTALL file.dsp
PKG UPDATE file.dsp

Choose the architecture that matches your system: 32-bit or 64-bit. Packages marked 16-bit DOS work on both editions. Install declared dependencies first.

Package manager API · v1

All read endpoints are public. Responses use JSON. Download URLs are absolute, and every release includes its byte size and SHA-256 digest. The API resolves a single package; dependency resolution is the client’s responsibility.

MethodEndpointPurpose
GET/api/v1/packages?q=curl&arch=64&page=1Search releases; 25 per page
GET/api/v1/resolve?name=curl&arch=64Latest compatible release; optional version
GET/api/v1/packages/1Release metadata
GET/api/v1/packages/1/downloadDownload; supports Range and ETag
POST/api/v1/packagesPublish one small package using a bearer token
POST/api/v1/uploadsStart a chunked upload: {"size": bytes}
PUT/api/v1/uploads/ID?offset=0Send the next chunk as the raw request body
GET/api/v1/uploads/IDBytes received so far, to resume
POST/api/v1/uploads/ID/completePublish the assembled package
DELETE/api/v1/uploads/IDCancel an upload

Fetch a package

PKG SEARCH curl
PKG INSTALL curl
PKG UPDATE curl

Online commands require the curl package. Packages larger than 50 MiB download as ranged 50 MiB chunks. The package manager verifies the size, SHA-256 and metadata before installation. The desktop manager’s Online tab uses the same catalog.

curl '{{ base }}/api/v1/resolve?name=curl&arch=64'

Other clients can read download_url from the response, download it, and verify sha256 and size before installation.

List responses include packages, total, page, per_page, and next_page (null on the final page). Add compatible=1 with an architecture to also list DOS packages. Native PKG uses format=inf for plain-text metadata.

Publish from build tools

Register, confirm your email and ask the administrator for publisher access. Create an API token in your account, then send a multipart upload:

curl --fail-with-body \
  -H "Authorization: Bearer $CATALOG_TOKEN" \
  -F 'package=@build/packages/curl-64.dsp' \
  '{{ base }}/api/v1/packages'

Proxies such as Cloudflare limit request bodies to 100 MB, so publish larger packages, or many at once, with the chunked upload script from the DOS-XC source tree:

CATALOG_TOKEN=... tools/publish_packages.py \
  --catalog '{{ base }}' build/packages/*.dsp

Chunked uploads send each chunk of at most 50 MiB (chunk_size in the upload response) in order. Each offset must equal received; a mismatched chunk returns 409 with the current received, so clients can resume. Unfinished uploads expire after 24 hours, and each publisher may keep 10 open. Completion returns the same release metadata as a direct upload.

Successful uploads return HTTP 201 and release metadata. Existing releases return 409. Other errors return JSON with an error string: 400 for invalid input, 401 for invalid credentials, 403 for a package name owned by someone else, 404 when no release exists, 410 for a deleted release or publisher, 413 for oversized requests, and 429 for rate limits.

Deleted releases retain their metadata pages, with installable: false and a null download_url. They are excluded from search and resolution. Downloads are blocked when a release or its publisher has been deleted.
