# DOS-XC TODO: Firefox support
**Goal:** a `firefox` package ("Firefox web browser") running real, current Firefox on the 64-bit edition, because the user needs modern websites. The user chose this knowing it is a very large project, after considering NetSurf and Ladybird. Do not reopen that choice. System changes are explicitly allowed. A `vlc` package ("VLC media player") is also wanted, later; it shares most prerequisites.

Older hardware checks that are still open: `git show 97064ed:TODO.md`.

## What already works (QEMU only, never on real hardware)
- **Threads:** kernel tasks sharing a process (`os/runtime/sched.c`), futexes, `os/libc/src/pthread.c`, thread-safe `errno`, `malloc`, stdio, emulated `__thread`. Passed a stress test on BIOS 32/64-bit and UEFI 64-bit. Documented in `docs/PROGRAMS.md`.
- **TLS:** OpenSSL 3.5.9 linked statically into curl and Python; Mozilla roots as `CACERT.PEM` in each package. Valid sites connect; expired, self-signed and wrong-host certificates are refused.
- **Randomness:** `DOSXC_SYS_RANDOM`, `os/runtime/random.c`. Not saved across restarts, which matters on CPUs without RDRAND. A saved seed is a good small improvement.
- **Python:** CPython 3.14.6 package, all extension modules static, real threads. Threads get 6 MiB stacks (`-DTHREAD_STACK_SIZE` in `scripts/build-ports.sh`) because CPython assumes about 4 MB when `pthread_getattr_np` is missing. Passed locks, queues, thread pools, `RecursionError` in a thread, and TLS from four threads at once on both editions.
- **GCC:** thread model `posix`. C `__thread`, C++ `thread_local`, `std::thread`, `std::mutex` and exceptions in threads work from the cross compilers and from the native package on both editions (native compiles only tested from a FAT32 disk with the package at `\Programs\GCC`).

## Firefox status (2026-11-10, QEMU 64-bit BIOS only)
Builds, packages and runs as a real window on the desktop: tabs, address bar, popup menus, keyboard, mouse, and live HTTPS pages through DOS-XC's network stack. Also verified: WebAssembly (traps reach JavaScript through fault delivery), HTTP/3 (cloudflare-quic.com reports it), IPv6 (a page served over IPv6 from the host), WebAudio through the `sound` package's HDA driver (recorded by QEMU), and Chinese, Japanese and Korean text (Noto Sans CJK). Packaged as `dosfox` (DOSfox: own name and pixel-art logo, `--with-branding=browser/branding/dosfox`). Start it from the Start menu (it is the default browser when installed), from a prompt, or with `DESKTOP.EXE X:\Programs\dosfox\DOSFOX.EXE`. Tested from the live media (unpacked tree added by `DOSXC_EXTRA_TREES_64`) and from a FAT32 disk with its profile there, the files copied on from the Mac. **`PKG INSTALL` onto a disk has not been tested**; it needs about 500 MB. Give the VM 6 GiB. The window appears about 25 s after launch under emulation. Native IDE/AHCI/NVMe drivers replaced the BIOS path (2026-11-10).

- [ ] `@mozilla.org/network/network-link-service;1` does not exist on this toolkit, so services.settings logs that it cannot tell the network status.
- [ ] `/proc/self/exe` drops the drive letter, so Firefox must be started with its own drive current. The Start menu entry assumes the system drive.
- [ ] `MOZ_CRASH` falls through to the `abort()` in `memory/mozalloc/mozalloc_abort.cpp`, because a null write does not fault here. It prints the reason and stack; symbolize with `x86_64-dosxc-nm` on the package's libraries.
- [ ] The title bar shows ASCII only; non-ASCII becomes `-`. Clipboard, cursor shapes, and drag and drop are not connected.
- [ ] UEFI boots have no preemption and are untested with Firefox.
- [ ] `<audio>` with a local `file:` WAV fails with `NS_ERROR_DOM_MEDIA_METADATA_ERR`; WebAudio works. Media over HTTP is untested.
- [ ] Sound is choppy under QEMU (21 ms bursts with gaps): the standalone driver test plays continuously, so the emulated CPU is probably too slow for Gecko's audio graph. Untested on hardware.
- [x] Opening DOSfox froze the desktop for minutes (2026-11-10): the kernel `memcpy` copied bytes one at a time, `fat32_read_at` read sector by sector and re-walked the cluster chain, and every task switch remapped all of libxul's private data. Now 8-byte copies, multi-sector reads (`read_sectors`) and a page-table tree per process (`aspace_*` in `os/runtime/paging.c`): the window appears in about 25 s under QEMU and the desktop stays usable meanwhile.
- [ ] File writes are about 4 MB/s on native disks: every cluster also writes the FAT sectors through (both copies). Needs FAT write-back caching.
- [ ] Keyboard modifiers now travel with key events (`DOSXC_CONSOLE_MODIFIERS`) but shortcuts like Ctrl+Shift+P have not been tried.

**Agreed order (2026-11-10):** finish the single-process bugs above first. Then process isolation as its own project: (1) ring 3 and per-process address spaces, (2) IPC and content processes, (3) a DOS-XC sandbox for them. Until (1) exists, Firefox must not be used on untrusted sites.

**Isolation progress:** (1a) done 2026-11-10 on 64-bit BIOS boots: programs run in ring 3 (own GDT entries and TSS, int 0x80 DPL 3, per-task 128 KiB kernel stacks, the timer switches tasks from ring 3, `\SYSTEM\RING0` turns it off); verified with a test program, the desktop and DOSfox. All pages still carry the U bit. (1b, part 1) done: each process has its own page-table tree (library data lives in it; a task switch loads CR3; threads share it; `vm.c` top-level entries are shared by all trees). (1b, part 2) done 2026-11-11: U only on the process's own memory (arena regions follow `memory_alloc`/`memory_free`, mappings are per tree, library images read-only), kernel pages supervisor-only, pointer checks for every system call (`check_arguments` in `os/runtime/system.c`), the desktop board shared with its clients and clients granted to the desktop (`process_share`, `process_grant`), the framebuffer for the display owner, the thread slot on its own page. Verified: a test program's reads and writes of kernel and other memory and kernel pointers passed to `read`/`write` fail; libctest (1366 checks) and syscalltest pass; the desktop, Explorer and DOSfox loading an HTTPS page work. `\SYSTEM\SHAREMEM` turns the separation off. Gaps: the desktop can still read every GUI client's memory; structures passed to multiplexed calls with unknown sizes are checked at their first byte only; 32-bit and UEFI boots stay ring 0 without isolation; no guard pages. Next: (2) IPC and content processes. Kernel IPC is done (see item 6). (2) and (3) written 2026-11-11. DOSfox with the content process (2026-11-11, QEMU, log only): starts its content processes and runs a local page for five minutes with no crash, IPC or graphics errors. Facts checked against the source on 2026-11-09 (`github.com/mozilla-firefox/firefox`, 162.0a1, shallow clone in `toolchain/work/firefox`, git-ignored): Rust 1.95+ is required; toolchains are only windows, cocoa, uikit, android, gtk3 (`toolkit/moz.configure`), with a `widget/headless` backend. **GCC 11.1+ is still accepted**, so the existing GCC 15 cross compiler can be used; Android alone requires Clang. **Single-process mode still exists:** `MOZ_FORCE_DISABLE_E10S=1` works in non-official builds (`toolkit/xre/nsAppRunner.cpp`), and fission follows. The first milestone is therefore a single-process browser, which needs neither item 5 nor most of item 6. It has no sandbox, so say so to the user before anyone browses untrusted sites with it.

1. **Memory: done; demand-paged on 64-bit only.** `<sys/mman.h>` on demand-paged mappings (`os/runtime/vm.c`). Documented in `docs/PROGRAMS.md`. `shm_open` and `mremap` (shrink only) are in libc. Shared file mappings are copies written back by `msync` and `munmap`, enough within one process. Not done: returning arena chunks.
2. **Address space: done for mappings on BIOS boots.** RAM above 4 GiB feeds mappings; tested with 8 GiB of RAM and 6 GiB touched. Identity-mapped programs and libraries still live below 4 GiB, and libxul will be loaded there. On UEFI, mappings only get the loader's block. Try `-m 8G` or more.
3. **Native TLS: done, 64-bit only.** `PT_TLS` in programs and libraries, FS base per thread, `__tls_get_addr`, and the `TPOFF64`, `DTPMOD64` and `DTPOFF64` relocations. Programs and libraries they start with use a static block; `dlopen`ed ones are allocated per thread, so an initial-exec library cannot be `dlopen`ed (the loader says so). GCC still emulates `__thread` (`--disable-tls`); both work together.
4. **`dlopen`: done.** `<dlfcn.h>`, `os/runtime/dynamic.c`, `os/libc/src/dl.c`. Limits are in `docs/PROGRAMS.md`. A library gets at most `MAX_PROCESS_LIBRARIES` (24) per process and `paging.c` has 128 page-table pages for private data; raise them if libxul runs out.
5. **Processes and isolation.** The largest change. Programs run in ring 0 in one shared address space; `spawn` is synchronous; there is no `fork`; `DOSXC_TASK_START` starts background programs. Firefox's content processes need asynchronous spawning, and running untrusted web content safely needs per-process page tables and ring 3. Per-process address spaces would also change the position-independent loading design, the library data swapping in `libraries_activate`, and the assumption that syscalls run on the program stack.
6. **IPC: kernel side done (2026-11-11).** `socketpair(AF_UNIX, SOCK_STREAM)` with `SCM_RIGHTS`, blocking and non-blocking, `poll`; shared memory objects (`memfd_create`, `shm_open`, `mmap(MAP_SHARED)` across processes). Verified between two isolated processes. Not done: named and datagram `AF_UNIX` sockets; remove the asyncio self-pipe patch in `python/python-dosxc.py` (needs a Python rebuild).
7. **Limits to raise.** `MAX_FDS`, `OPEN_MAX` and `FD_SETSIZE` are 1024 (raised from 64 on 2026-11-10: Firefox ran out), sockets 256 system-wide, `MAX_DEPTH` is 32 processes, 256 task slots system-wide (`MAX_TASKS`, 32 KiB kernel stack each), 2 MiB default thread stacks with no guard pages. Also missing: `sys/un.h`, `sys/shm.h`, `ifaddrs.h`, `pthread_getattr_np`, per-thread signals. Cancellation only happens at `pthread_testcancel`, condition waits and joins. `fork` returns `ENOSYS`.
8. **Rust: works, with no new target.** Stock `x86_64-unknown-linux-musl` std, linked by `x86_64-dosxc-gcc` against DOS-XC's libc: threads, thread-locals, channels, files, DNS and TCP, panics, and all of that inside a `dlopen`ed cdylib. The libc matches Linux's layouts where Rust looks (64-bit `struct stat`, constants) and provides `syscall()` for futex and getrandom (`os/libc/src/linux.c`). Link flags: `--target x86_64-unknown-linux-musl -C target-feature=-crt-static -C link-self-contained=no -C linker=x86_64-dosxc-gcc`, and `-L` a folder with `libgcc_s.a` as a copy of libgcc.a. Rust 1.99.1 is in `toolchain/work/rustup`. `struct sigaction` and `sigset_t` still differ from musl; Rust only uses them for its stack-overflow handler.
9. **Firefox platform layers: done for one process.** System malloc instead of mozjemalloc, sandbox off, audio backends off, Linux personality via `-D__linux__`.
10. **Widget backend: done.** `widget/dosxc` draws software WebRender frames into a desktop window (see `firefox/README.md`). Popups are borderless windows (`struct window.popup`). The JIT is left enabled; whether it is actually used has not been checked.
11. **Later.** IPv6, a fuller TCP stack (see limits below), fonts, a sound driver and cubeb backend, video.

Networking limits today: IPv4 only, no fragment reassembly, 64 KiB TCP windows, NICs polled from system calls (`net_tick`) with no interrupts.

## How to test
```sh
python3 tests/qemu_session.py --iso build/iso/DOSXC_0.2_x64.iso --timeout 240 \
  --qemu-arg="-netdev user,id=n0 -device e1000,netdev=n0" \
  -c 'PKG INSTALL X:\Packages\ethernet.dsp /Y' -c 'PKG INSTALL X:\Packages\python3.dsp /Y' -c '~10' -c 'PYTHON3 X:\T\TEST.PY'
```
- `-c '~N'` waits, `-c '&TEXT'` types without waiting for a prompt, `-c '!cmd'` is a QEMU monitor command. `--uefi` takes a firmware file, `--screendump` writes a PPM.
- Put test programs on the media with `DOSXC_EXTRA_TREES=dir scripts/build.sh`; they appear at the root of `X:`.
- Build test media in a separate folder with `BUILD=/some/dir`. **`scripts/build.sh` deletes `build/iso`, so check the user has no QEMU running from it.**
- Cross-compile a test: `x86_64-dosxc-gcc --sysroot=toolchain/work/ports-x86_64/sysroot -O1 t.c -o T.EXE`.

## Things that cost time
- The live system's RAM disk is small: Python and Vim do not both fit, and a failed install reports "is the disk full?". Test big packages one at a time or on a real disk. Nothing has been tested from a hard-disk install yet.
- Ports link `libc.so` dynamically, so old installed systems (including any existing `build/disk.img`) need reinstalling from a current ISO.
- Autotools ports need help: CPython's link tests silently all fail without `--with-suffix=.exe`, because the toolchain writes `conftest.exe`. Set `PKG_CONFIG=false` or host libraries leak in.
- Paths are `C:/...` with `;` search paths. Anything assuming `/`-rooted paths or `:` separators breaks; expect this in Firefox's build output and at run time.
- Native GCC looks for headers in `/Programs/GCC/include` on the **current drive**. Run it from the drive GCC is installed on or it reports `wchar.h` as missing.
- A header that defines different things depending on include order can silently change struct layouts. CPython's `CONDATTR_MONOTONIC` needs `CLOCK_MONOTONIC`, so `<pthread.h>` must include `<time.h>`; without it `_hashlib` saw `_PyRuntime` 8 bytes larger than the core did and crashed. A jump to an address containing `F000FF53` means a call through a null object: low memory holds the BIOS vector table. Expect more of this with Firefox, whose headers assume glibc includes.
- For a test crash use `__asm__("ud2")`. GCC folds `1 / z` to a conditional with no division, and low addresses are mapped, so a null write does not fault.
- Preemption only happens on BIOS boots (100 Hz, program code only). Under UEFI, threads switch only at system calls, so spinning code stalls others. Firefox on UEFI will need a real timer.
- Update `docs/` alongside system changes; the project keeps them accurate.
